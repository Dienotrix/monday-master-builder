# monday gotchas

The one dated list of what the monday API cannot say about itself (A§10.2). Skills and references link to an entry by its id and never restate it. Every entry comes from the live runs of 2026-09-10 and 2026-09-11 in the test workspace, the three recheck passes, the native structure run of 2026-09-11, and the probes and recapture of 2026-09-12. Nothing here comes from a learn file, from documentation alone, or from memory.

**How to read an entry.** Every entry carries the same eight facts: the claim; the surface (a tool by base name, or "raw" for a GraphQL document sent through `all_api_read`, `all_api_write`, `all_monday_api` or `execute_code`); the ring the probe observed; what to do instead; the evidence with its date; the probe that re-tests it, as a recipe id in `probe-catalog.md` (`monday-drift-check`), marked read-only or sandbox write; its impact; and its status. High-impact entries carry the full block; the rest carry the same eight facts on one line under their heading. Ids never renumber; a retired entry keeps its id for one release.

**Status vocabulary:** `confirmed` (executed with a control or a recheck that agreed), `observed` (executed once, or the recheck read differently and the more controlled read is reported), `docs`, `untested` (always carries a safe default), `retired` (kept for one release with the date it stopped being true). A read-back that contradicts an entry wins for that build, is logged as an `api-surprise`, and suggests a drift check; it never edits this file (A§10.3).

## 1. Tool boundaries, versions and limits (G-01 to G-06)

## G-01 · The read tool can write, and the write tool can read
Claim: `all_api_read` refuses a lone mutation but runs the first operation of a two-operation document, so a mutation placed first goes through; `all_api_write` returns data the same way for a query placed first. Surface: `all_api_read`, `all_api_write` (raw). Ring: release_candidate 2026-10. Do instead: send one operation per document; never treat the tool's name as a boundary. A2 settles that no document-parsing guard is required: the auditor uses the normal read tools and its independence is proved by before-and-after snapshots and the scan of every document it sent (A§9.7). Evidence: executed with read-back, 2026-09-11 (raw-writes-lifecycle: a mutation-first document changed a board description; recheck-1 and recheck-2 reproduced the bypass). Probe: sandbox write, recipe P-G01 in probe-catalog.md. Impact: medium. Status: confirmed.
## G-02 · The connector runs a release candidate; the code sandbox runs current
Claim: the connector's GraphQL tools serve `release_candidate 2026-10`; `execute_code` calls with no `API-Version` header are served `2026-07`, and the two rings have different schemas (96 queries and 196 mutations against 107 and 229). Surface: `all_api_read`, `all_api_write`, `all_monday_api`, `execute_code`. Ring: release_candidate 2026-10 (sandbox default 2026-07). Do instead: send `API-Version` on every raw call and record `version { kind value }` and `versions` with every change check and preflight (A§10.5). Evidence: executed, 2026-09-11 (meta-and-reads; the sandbox `Api-Version` response header read with and without the request header; recheck-1 agrees). Probe: read-only, recipe P-G02 in probe-catalog.md. Impact: medium. Status: confirmed.
## G-03 · Schema tools hide deprecated members that still work
Claim: `get_graphql_schema` and `get_type_details` omit deprecated members that still work on 2026-10 (`Column.settings_str`, `Board.owner`, `Board.activity_logs`, `add_subscribers_to_board`); raw introspection with `includeDeprecated: true` shows them, and fourteen User fields deprecated in 2026-07 no longer exist in 2026-10. Surface: `get_graphql_schema`, `get_type_details`; raw introspection. Ring: release_candidate 2026-10. Do instead: run drift checks with raw introspection and `includeDeprecated: true` per pinned ring; build on nothing removed from User. Evidence: executed, 2026-09-11 (meta-and-reads; three read paths agree; recheck-1 agrees for 2026-10 and 2026-07). Probe: read-only, recipe P-G03 in probe-catalog.md. Impact: medium. Status: confirmed.
## G-04 · Live quotas differ from documented numbers, and the read tool returns no headers
Claim: this account's `RateLimit-Policy` headers allowed 7,335 requests a minute, 500 concurrent and 20,000,000 complexity a minute, with `platform_api.daily_limit` base 25,000 and total 50,000; `all_api_read` returns the body only, so headers are readable from `execute_code` alone, which injects auth itself. Surface: `execute_code` (raw headers); `all_api_read` (`platform_api`). Ring: release_candidate 2026-10 and 2026-07. Do instead: read limits at preflight and never hard-code a quota; quote no limit that was not read live on the client's own account (never-say row 8). Evidence: executed, 2026-09-11 (meta-and-reads; recheck-1 agrees). Probe: read-only, recipe P-G04 in probe-catalog.md. Impact: medium. Status: confirmed.
## G-05 · The knowledge tool gets connector behaviour wrong
Claim: asked which API version the hosted connector uses, `get_monday_knowledge` said its sources did not say, then reasoned 2026-07 while the connector serves 2026-10, with an empty sources array; it is also rate-limited across the whole client account. Surface: `get_monday_knowledge`. Ring: release_candidate 2026-10. Do instead: take connector and API behaviour only from live reads; use the tool for UI how-to a client admin must perform (A§10.1). Evidence: executed against `version{}`, 2026-09-11 (meta-and-reads; recheck-1 agrees). Probe: read-only, recipe P-G05 in probe-catalog.md. Impact: low. Status: confirmed.
## G-06 · Errors come back as one string with no partial data
Claim: `all_api_write` and `all_monday_api` report a failure as one message, `Failed to execute GraphQL operation: <message> (details: {code, error_data})`, with no data object and no `errors[].extensions`; the item tools add their own prefix; `ColumnValueException` details name `column_type` under internal names (numeric, lookup, formula) and a bad status label lists the valid labels; only `update_items` returns structured `errors[]` with `path ["results", i]`. Surface: `all_api_write`, `all_monday_api`, `create_item`, `change_item_column_values`, `update_items`. Ring: release_candidate 2026-10. Do instead: parse the details JSON out of the message text, and after any raw write that errors read the stored state back rather than assuming nothing happened (G-37, G-38). Evidence: executed with read-back, 2026-09-11 (items-values: failed creates left no item, `updated_at` unchanged after failed updates). Probe: sandbox write, recipe P-G06 in probe-catalog.md. Impact: medium. Status: confirmed.

## 2. Inventory, search and read-back (G-07 to G-11)

## G-07 · Search can prove neither that an object exists nor that it does not
Claim: a nonsense term scoped to the workspace never returned an empty set (BOARD 16, then 20; ITEMS 20, the maximum; DOCUMENTS 1); an exact name only moved that board to the top; boards created minutes earlier were missing until the index caught up; DOCUMENTS hits carry the container board id, not the doc id. Surface: `search`. Ring: release_candidate 2026-10. Do instead: never decide existence from search; use exact reads (`boards(workspace_ids, state: all)`, `docs(workspace_ids)`, `items_page` rules) and confirm every hit by id. Evidence: executed, 2026-09-11 (meta-and-reads; recheck-1 re-ran BOARD search, 20 results with the lagging boards present). Probe: read-only, recipe P-G07 in probe-catalog.md. Impact: medium. Status: confirmed.
## G-08 · workspace_info is not a full inventory
Claim: it omits dashboards, archived boards and board types, mixes doc containers, subitems boards and workflow boards in with real boards, reports description "" where GraphQL says null, has no `account_product`, and caps at 100 per object type; on 2026-09-11 it listed 24 boards where `boards(workspace_ids, state: all)` listed 25. Surface: `workspace_info`; raw `boards`. Ring: release_candidate 2026-10. Do instead: build inventories from `boards(workspace_ids, state: all)` with `type` and `state`, add docs, track dashboards separately, and read workspace kind and product through GraphQL. Evidence: executed, 2026-09-11 (meta-and-reads; recheck-1 agrees; the consolidation's reconciliation matched). Probe: read-only, recipe P-G08 in probe-catalog.md. Impact: medium. Status: confirmed.
## G-09 · Archived boards vanish from default reads; archived items do not
Claim: after `archive_board`, `boards(ids)` returns `[]` without `state: all`, `workspace_info` drops the board and `get_board_info` says not found; `items(ids)` still returns an archived item marked `archived` while the board's default `items_page` hides it; archiving a board does not change its items' state. Surface: raw `boards`, `items`, `items_page`; `workspace_info`, `get_board_info`. Ring: release_candidate 2026-10. Do instead: every resume and inventory read passes `state: all`, or archived boards get created again; check `state` on any item read by id. Evidence: executed with read-back, 2026-09-11 (raw-writes-lifecycle; recheck-2 agrees). Probe: sandbox write, recipe P-G09 in probe-catalog.md. Impact: medium. Status: confirmed.
## G-10 · Hidden board types show up in board lists
Claim: `boards(workspace_ids, state: all)` returns ordinary boards, `document` doc containers, `sub_items_board` and `custom_object` (a workflow object with default columns, two groups and a FeatureBoardView); multi-level boards are in the default listing on both rings and `hierarchy_types: [classic]` excludes them. Surface: raw `boards`; `workspace_info`, `get_board_info`. Ring: release_candidate 2026-10 and 2026-07. Do instead: filter by `type` and `hierarchy_type`; find subitems boards through the subtasks column's `settings.boardIds` (G-44). Evidence: executed, 2026-09-11 (boards-folders-hierarchy; recheck-1 and recheck-2 agree). Probe: read-only, recipe P-G10 in probe-catalog.md. Impact: medium. Status: confirmed.
## G-11 · Dashboards and widgets cannot be read back
- Claim: no query returns a dashboard's widgets or their settings; a Widget object comes back only from `create_widget`; search finds dashboard metadata but not widgets; raw `search.overviews` errors with DOWNSTREAM_SERVICE_ERROR when `live_data` is selected; `objects(ids)` returns workflow objects but not dashboards; there is no `update_widget`, and `update_dashboard` changes only name, workspace, kind and folder.
- Surface: `create_widget`, `search`; raw schema. Ring: release_candidate 2026-10.
- Do instead: store every widget id and its settings at creation; verify dashboards by eye and put them on the user's click-through list; to change a widget, delete it by id and create it again (G-89, G-90).
- Evidence: executed with a full scan of the 1,380-type schema, 2026-09-11 (dashboards-widgets; recheck-2 agrees).
- Probe: read-only, recipe P-G11 in probe-catalog.md.
- Impact: high. Status: confirmed.

## 3. Boards and folders (G-12 to G-20)

## G-12 · create_board ignores folderId unless creationPrompt is sent
Claim: without `creationPrompt`, five tool-created boards (plain, multi-level flag, dataset flag, private kind) passed `folderId` and landed at the workspace root; with a prompt the board went into the folder; raw `create_board(folder_id)` placed correctly with or without `empty: true`. Surface: `create_board`; raw `create_board`. Ring: release_candidate 2026-10. Do instead: read `board_folder_id` after every tool-created board and `move_object` when it is null, or create raw with `folder_id` and `empty: true` (A§12.1 C2). Evidence: executed with read-back of `board_folder_id` and the folder's children, 2026-09-11 (boards-folders-hierarchy; recheck-1 agrees; the cause is inferred, not proven). Probe: sandbox write, recipe P-G12 in probe-catalog.md. Impact: medium. Status: confirmed.
## G-13 · move_object places a board in a folder
Claim: `move_object(objectType: Board, id, parentFolderId)` answered "Board position updated" and the board read back inside the folder in both `board_folder_id` and the folder's children; the same call can also change workspace and account product (G-106). Surface: `move_object`. Ring: release_candidate 2026-10. Do instead: use it as the placement fix after creation and read the result back. Evidence: executed with read-back, 2026-09-11 (boards-folders-hierarchy; recheck-1 agrees). Probe: sandbox write, recipe P-G13 in probe-catalog.md. Impact: low. Status: confirmed.
## G-14 · Raw create_board adds a sample item unless empty: true
Claim: raw `create_board` without `empty: true` made the "Group Title" group plus a sample item "Task 1"; with `empty: true` no items; tool `create_board` without a prompt gave one group, the Name column, no items and a null description. Surface: raw `create_board`; `create_board`. Ring: release_candidate 2026-10. Do instead: pass `empty: true` on every raw create, or archive the sample item before seeding. Evidence: executed with read-back on six boards, 2026-09-11 (boards-folders-hierarchy; recheck-1 agrees). Probe: sandbox write, recipe P-G14 in probe-catalog.md. Impact: low. Status: confirmed.
## G-15 · creationPrompt builds scaffolding, not a finished board
Claim: one short prompt produced a generated description, three groups (the default renamed "To Do", plus "In Progress" and "Done"), a Status column with labels To Do (id 17), In Progress (id 0) and Done (id 1), a Due Date column, no items, no views, and generated column ids such as `color_mm73h0ss`. Surface: `create_board` (`creationPrompt`). Ring: release_candidate 2026-10. Do instead: treat prompt output as a starting point; read back column ids, label ids and groups before writing any value. Evidence: executed with read-back, 2026-09-11 (boards-folders-hierarchy; recheck-1 agrees; visible group order unchecked). Probe: sandbox write, recipe P-G15 in probe-catalog.md. Impact: low. Status: confirmed.
## G-16 · Template flags create sample items, and multi-level items hide from default reads
Claim: `useMlsTemplate: true` made a real `multi_level` board with People, Status, Subitems and Timeline columns and four sample items nested three levels deep, of which the default `items_page` showed one and `hierarchy_scope_config: "allItems"` showed all; `useDatasetTemplate: true` made a classic board with three sample items; both flags ignored `folderId`. Surface: `create_board`; raw `items_page`. Ring: release_candidate 2026-10. Do instead: allow either flag only when the frozen revision lists it as an irreversible item with sample cleanup planned (A§9.4); read nested items with `allItems`; move the board into its folder afterwards. Evidence: executed with read-back, 2026-09-11 (boards-folders-hierarchy; recheck-1 agrees). Probe: sandbox write, recipe P-G16 in probe-catalog.md. Impact: medium. Status: confirmed.
## G-17 · Item terminology needs a JSON value
Claim: raw `update_board(board_attribute: item_nickname, new_value: '{"singular":"task","plural":"tasks","preset_type":"task"}')` changed `item_terminology`; a plain `"task"` failed twice with INTERNAL_SERVER_ERROR and changed nothing; the `create_board` tool has no nickname argument. Surface: raw `update_board`. Ring: release_candidate 2026-10. Do instead: set terminology after creation with the JSON string and read `item_terminology` back; treat a 500 here as a wrong payload shape. Evidence: executed with read-back, 2026-09-11 (boards-folders-hierarchy; recheck-1 confirmed the stored state, did not re-run the failing call). Probe: sandbox write, recipe P-G17 in probe-catalog.md. Impact: low. Status: confirmed.
## G-18 · Private boards: read board_kind; only the creator is a member
Claim: `boardKind: private` read back `board_kind: private` with the creator as the only owner and subscriber; Board has no field `kind` and querying it errors; `change_board_kind` exists and was not run. Surface: `create_board`; raw `boards`. Ring: release_candidate 2026-10. Do instead: read visibility from `board_kind`; plan handoff and cleanup of private boards with their owner, since nobody else can see them. Evidence: executed with read-back, 2026-09-11 (boards-folders-hierarchy; recheck-1 agrees). Probe: sandbox write, recipe P-G18 in probe-catalog.md. Impact: low. Status: confirmed.
## G-19 · A structure-only duplicate keeps ids and copies the description
Claim: raw `duplicate_board(duplicate_type: duplicate_board_with_structure, workspace_id)` returned synchronously (`is_async` false), kept every group id, colour and position and every column id and label setting, copied the description, carried no items and landed at the workspace root; all three `DuplicateBoardType` values copy structure, and no `duplicate_board` tool exists, so duplication always arrives as raw text (G-106). Surface: raw `duplicate_board`. Ring: release_candidate 2026-10. Do instead: pass `workspace_id` and `folder_id`, check `is_async`, rewrite the copied description; never duplicate a board in the native index (A§9.10). Evidence: executed with read-back, 2026-09-11 (raw-writes-lifecycle; recheck-2 agrees; the default landing place and copying from inside a folder untested). Probe: sandbox write, recipe P-G19 in probe-catalog.md. Impact: medium. Status: confirmed.
## G-20 · Archive has no named undo; undo_action is untested
- Claim: `archive_item` and `archive_board` work and read back as archived; no mutation named unarchive or restore exists for items or boards (only `restore_view`); recheck-2 found `Mutation.undo_action(job_id)` and an `action_record_uuid` on archive events in `get_board_activity`, while the archive calls return no job id.
- Surface: raw `archive_item`, `archive_board`, `undo_action`; `get_board_activity`. Ring: release_candidate 2026-10.
- Do instead: treat every archive as irreversible for an agent — its own yes with containment evidence, ids confirmed first, every archive recorded in the ledger, `state: all` in every inventory (A§9.4). The safe default stands until P-3 runs and `undo_action_verified` is written to the overlay.
- Evidence: the archive executed with read-back, 2026-09-11 (raw-writes-lifecycle; recheck-2 found the possible API path); the undo itself has never been run.
- Probe: sandbox write, recipe P-G20 in probe-catalog.md (archive a throwaway item, take its `action_record_uuid`, call `undo_action`, read the state).
- Impact: high. Status: untested.

## 4. Groups, columns and settings (G-21 to G-34)

## G-21 · Group colour rules differ between create and update
Claim: on create, palette hex values and underscore names are applied, while an off-palette hex or the plain word "green" is replaced without error and the no-colour default varies (#a25ddc once, #c4c4c4 once); on update, `update_group(group_attribute: color)` refuses hex and underscore names ("Input color is not in colors options") and accepts plain words. Surface: `create_group`; raw `create_group`, `update_group`. Ring: release_candidate 2026-10. Do instead: create with a palette hex and read `groups { color }` back; recolour with `update_group` and a plain colour word; never assume a default colour. Evidence: executed with read-back, 2026-09-11 (raw-writes-lifecycle; recheck-2 confirmed each colour through the activity log). Probe: sandbox write, recipe P-G21 in probe-catalog.md. Impact: low. Status: confirmed.
## G-22 · Status label ids are not positions
- Claim: without an explicit id a label's id is its colour number (sky 158, berry 104, done_green 1, purple 4), not its position; explicit ids are kept exactly; a written `{index: N}` means label id N, so `{index: 2}` fails with missingLabel on a column with no id 2 while `{index: 104}` stores that label; the tool's status schema enumerates colour numbers.
- Surface: `create_column` (tool and raw), `change_item_column_values`, `get_column_type_info`; raw `columns { settings }`. Ring: release_candidate 2026-10.
- Do instead: set explicit ids when a filter, widget, automation or index write depends on them; read label ids from `settings` before writing by index; prefer writing status by label text; a label change is a change-table row with dependants read live (A§9.4).
- Evidence: executed with read-back, 2026-09-11 (columns-settings; items-values; recheck-1 agrees).
- Probe: sandbox write, recipe P-G22 in probe-catalog.md.
- Impact: high. Status: confirmed.

## G-23 · Wrong status filter forms silently return nothing
- Claim: `any_of` with label ids matched; `any_of` with label text returned zero items and no error; `contains_terms` with text matched; `contains_terms` with an id returned zero and no error; tool and raw `items_page` behave the same, and the `[0,1]` example in `get_column_type_info` misleads because ids are not positions.
- Surface: `get_board_items_page`; raw `items_page` (`query_params`). Ring: release_candidate 2026-10.
- Do instead: filter with `any_of` plus ids read from settings, or `contains_terms` plus text; before trusting an empty result, run the same filter form against a known item.
- Evidence: executed, 2026-09-11 (items-values; recheck-1 agrees).
- Probe: read-only, recipe P-G23 in probe-catalog.md.
- Impact: high. Status: confirmed.

## G-24 · A default "Done" label is not marked done
Claim: on two boards a status column created without settings carried a "Done" label whose `is_done` was false; a battery that follows `is_done` could show 0%, which is unverified. Surface: `create_column`, raw `create_column` (status, no settings). Ring: release_candidate 2026-10. Do instead: set `is_done` explicitly on every status column that feeds a battery or done logic, and read it back. Evidence: executed with a settings read on two boards, 2026-09-11 (columns-settings; recheck-2 saw the same through `get_board_info`). Probe: sandbox write, recipe P-G24 in probe-catalog.md. Impact: medium. Status: confirmed.
## G-25 · Dropdown labels must be objects; raw string defaults give an empty dropdown
Claim: the tool rejected plain-string labels (INVALID_INPUT `labels/N must be object`) and made no column; label objects work, explicit ids kept and otherwise 1..n; raw `create_column` with a JSON string of plain labels created the column with no labels and no error. Surface: `create_column`; raw `create_column` (`defaults`). Ring: release_candidate 2026-10. Do instead: send labels as objects and check the labels list is not empty after creation. Evidence: executed with read-back, 2026-09-11 (columns-settings; recheck-1 agrees on the stored labels). Probe: sandbox write, recipe P-G25 in probe-catalog.md. Impact: medium. Status: confirmed.
## G-26 · A settings wrapper is accepted on create and rejected on update
Claim: `create_column` accepted `{"settings": {...}}` on both paths and stored the inner settings; `update_column` rejected the same wrapper with INVALID_INPUT `data/settings must NOT have additional properties`. Surface: `create_column`, `update_column`; raw `create_column`. Ring: release_candidate 2026-10. Do instead: send flat settings everywhere (A§12.1 C3). Evidence: executed with read-back, 2026-09-11 (columns-settings; recheck-1 agrees). Probe: sandbox write, recipe P-G26 in probe-catalog.md. Impact: low. Status: confirmed.
## G-27 · settings and settings_str return different shapes
Claim: `Column.settings` gives dropdown labels under `label` and a mirror's `displayed_linked_columns` as a list of `{board_id, column_ids}` objects; the deprecated `Column.settings_str` still works and gives labels under `name` and the same field as a map keyed by board id; the shape depends on which field is read. Surface: raw `Column.settings`, `Column.settings_str` (hidden by the schema tools, G-03). Ring: release_candidate 2026-10 and 2026-07. Do instead: pick one field per code path and parse that field's shape; prefer `settings`. Evidence: executed, 2026-09-11 (columns-settings; recheck-1 showed both shapes coexist, which settles the probe's earlier claim that the old shape had gone). Probe: read-only, recipe P-G27 in probe-catalog.md. Impact: medium. Status: confirmed.
## G-28 · Number units persist as sent
Claim: `{unit: {symbol: "$", direction: "left", precision: 2}}` stored exactly; non-currency units use `symbol: "custom"` plus `custom_unit`; `settings` and `settings_str` were identical here. Surface: `create_column`; raw `columns { settings }`. Ring: release_candidate 2026-10. Do instead: send a flat unit object, `custom` plus `custom_unit` for anything but currency, and read it back. Evidence: executed with read-back, 2026-09-11 (columns-settings; recheck-1 agrees). Probe: read-only, recipe P-G28 in probe-catalog.md. Impact: low. Status: confirmed.
## G-29 · Relation columns can be re-targeted in place; every update must resend boardIds
Claim: a `board_relation` created with settings `{}` was repaired with `update_column {boardIds: [...]}` and linked afterwards; a later update sending only `allowMultipleItems` failed with INTERNAL_SERVER_ERROR on both paths and changed nothing, while resending `boardIds` with it worked and kept the links; the `change_item_column_values` response showed the relation as null although the link was stored. Surface: `update_column`, `change_item_column_values`; raw `update_column`. Ring: release_candidate 2026-10. Do instead: repair unwired relations in place, include `boardIds` in every relation settings update, and prove links from a `linked_item_ids` read, never from the write response. Evidence: executed with read-back of settings, revision and `linked_item_ids`, 2026-09-11 (columns-settings; recheck-1 confirmed the stored state; the 500 was not re-run). Probe: sandbox write, recipe P-G29 in probe-catalog.md. Impact: medium. Status: confirmed.
## G-30 · update_column checks the revision, and an empty string skips the check
Claim: `update_column` requires `revision` (String!); a stale or invented value fails with REVISION_MISMATCH 409 "Board revision mismatch" and applies nothing, though the check uses the column's own revision; an empty string skips the check on both paths and the change is applied; a successful update rotates only that column's revision; the tool's description points at `get_board_schema`, which this connector does not have. Surface: `update_column`; raw `update_column`. Ring: release_candidate 2026-10. Do instead: read `Column.revision` immediately before each update and send it; never send "", which switches the concurrency check off. ## Never say

A claims block, not a gotcha: the per-entry fields above do not apply to it. `demo-script` reads it at generation (A§3.5) and `house-style.md` links its DON'T list here; `call-intake` uses it when it writes the deferred-answer register. Each row is a claims rule tied to the probe evidence behind it, with the sentence that replaces the claim. Rows 8 to 12 are the five the calibration added (`REAL-CALL-LESSONS.md` C51); rows 13 to 15 are its three companion rules that name this file (C46, C92, C101).

1. Never describe a multi-object asynchronous setup as a one-time mapping. Instead: name the boards a portfolio or project creates, that they arrive seconds later, and that connecting deletes one of them [G-71, G-72, G-77].
2. Never promise a dashboard or a view as working when its widgets cannot be read back. Instead: "the settings were accepted; someone looks at it before we call it done" [G-11, G-89, G-90].
3. Never promise a bulk action at a scale we have not run. Instead: state the batch sizes actually run (20 creates, 40 updates, about 450 doc blocks) and that anything beyond about 500 rows is deferred [G-36, G-37, G-54, A§14].
4. Never answer a cascade edit with an unqualified yes. Instead: "a label or column change reaches everything that depends on it; we read the dependants live and change it as a listed step" [G-22, G-23, A§9.4].
5. Never state a nesting depth. Instead: state the consequence — a parent's values become roll-ups of its leaves, filters return top-level items only, and forms cannot ask about the calculated columns [G-75, G-76, G-82, G-88].
6. Never make an "as long as the names match" integration claim, including identifier matching by domain or name. Instead: name the id the two sides share and how it is read back; names decide nothing [G-07, G-42, G-97].
7. Never promise an automation as maintenance-free. Instead: "it is live from the moment it exists, and switching it off is a step in monday that we hand over" [G-65, A1].
8. Never quote a scale number that was not read live on the client's own account at prep, and never a roadmap statement that a limit will rise. Instead: say where the practical ceiling comes from in their workflow and offer to read the live limit [G-04, G-90].
9. Never answer a permissions question with a views answer. Instead: "a filtered view hides, it does not restrict, and it is one careless edit from showing everything"; board-level permissions are proved by a read, everything below is checked by eye [G-87, G-108].
10. Never state a file-count or file-size limit, and never "the limits are massive". Instead: the mechanism and its two known edges — an upload URL that lasts 15 minutes and no way to delete an asset — because no probe measures the rest [G-58, G-59].
11. Never describe metered-allowance behaviour — expiry, reset, whether a run consumes credit — from memory. Instead: record what the client's admin can see and measure it, because two of our own people gave opposite answers in two calls; no probe measures it [G-04 for the nearest live read].
12. Never repeat a figure or promise inherited from a colleague's earlier meeting until it is verified with that colleague. Instead: the corrections block at the top of the run-sheet, attributed to us [A§9.12; no probe].
13. Never say "it can" for something we have not shown or built: only shown and buildable may be stated as capability, and shown names the account and plan it was shown on. Instead: "I would want to check that before I promise it", then build the smallest working version, run it once and multiply by their own volume [G-64, G-89; C46].
14. Never say "we can change it later" unqualified about a fork. Instead: what conversion does and does not restore — a subitem board and a question's column stay, connecting a project deletes its overview, converting a board is one-way [G-44, G-49, G-77, G-80; C92].
15. Never assert a capability, limit or flexibility of a third-party system nobody on our side has read. Instead: quote what the client's own systems owner said, attributed, and name the document to read first [no probe; C101].
