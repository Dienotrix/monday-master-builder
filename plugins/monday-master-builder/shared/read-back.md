# Read-back: the read that proves each write

One home for the proof after every write (A§10.4). A monday capability has three outcomes — rejected, works, accepted with no effect — and only a read-back separates the last two. So every write in the build order (A§8.6 step 16) runs the same sequence: `ledger.py intent` → `leak_lint.py --payload` → the call → `ledger.py record` → the read named below → `ledger.py verify match|mismatch|not-checkable`. `verify.result` takes a fourth value, `needs-user`, from the ledger schema (A§7.3): `not-checkable` means no API read exists for what was written, and the audit records who checks it and how; `needs-user` means the object's existence is proved by id but its effect can only be seen in the monday UI. Neither is ever reported as verified. The verify `read` field in `build.json` stores the read string from this file.

Every `[live G-nn]` mark below is the 2026-09-10/11 run on ring `release_candidate 2026-10` (`shared/monday-gotchas.md` carries the entry); `[live P-nn 2026-09-12]` is the later probe run on the same ring; `[doc]` is documentation not yet proved by a write of our own. Native detection reads live in `shared/native-objects.md` and are not repeated here.

## Rules that apply to every read

- A build's raw read is passed through `gql_guard.py scan` before it is sent — one operation, no mutation — because `all_api_read` runs a mutation placed first in a two-operation document [live G-01]. The auditor's reads are not gated (A2); its appendix is scanned afterwards, which is how a write during an audit is detected (A§12.4). `execute_code` reads pin `API-Version`, and `version{kind value}` is recorded with each verification [live G-02].
- Every board read passes `state: all`; without it an archived board vanishes and a resume creates it again [live G-09]. Every `boards(ids:)` read diffs the requested ids against the returned ids, because the API drops an id it cannot return with no error and no placeholder; a missing id is `unreadable`, never deleted and never absent (A§11.1). The read-back records that shape: `requested_ids`, `returned_ids`, `missing_ids`.
- Column configuration is read from `settings`, never `settings_str`, which is deprecated and uses different keys [live G-27]. The schema tools hide deprecated members that still work, so a drift read introspects raw with `includeDeprecated: true` [live G-03].
- `search` never proves that something exists or that it does not [live G-07], and `workspace_info` is not an inventory: it omits dashboards, archived boards, board types and `account_product` [live G-08]. Inventories come from `boards(workspace_ids, state: all)` with `type`, `state` and `created_at`, plus `docs(workspace_ids)`, folders, and dashboards by stored id (A§8.11).
- The activity log is evidence of what a create stored and of an archive's `action_record_uuid`; it records no board description edit, no refused call, and nothing for an archived board [live G-70].
- The MCP items reader cannot read a mirror and `MirrorValue.text` and `BoardRelationValue.text` are null, so every mirror or relation value is read raw through `display_value`, `mirrored_items` or `linked_item_ids` [live G-31, G-79].
- A read-back that contradicts a gotcha wins for that build, is logged as an `api-surprise`, and suggests `/monday-drift-check`; nothing in a client chat edits this file or the knowledge overlay (A§10.3).
- Before a `not-checkable` is recorded for a capability, the call form is varied once — id or name, string or object, tool or raw, flat or wrapped (A§10.1).

## The by-eye list

What the audit hands to the user with the object's id and what to look for, because no API read sees it: every created widget and whether the dashboard renders the data its settings name (V-01); permissions below board level; a doc image after upload (V-02); whether a form renders and accepts responses; a Gantt, Snapshot or planner tab; and, for every automation, that the switch-off step in the handoff works for the person who follows it (U-01). Each row is `needs-user` or `not-checkable` in the ledger, never `match`.

## What the audit builds from these reads

The before and after digests of A§9.7 come from the same reads: columns (id, title, type, revision, settings), groups, view settings, owners and subscribers per in-scope board; automations (id, active, `updated_at`); forms through `get_form`; doc block counts by raw paging; dashboards by stored id. A row the audit cannot digest — a widget, a permission below board level — is listed for the user's eyes rather than digested as empty, which is why widget changes stay undetectable and every widget is listed.
