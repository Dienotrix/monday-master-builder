# Record map

The one home for the client record: its files, owners, budgets, schemas, vocabularies and every string the scripts look for. It carries A§7 of the architecture as amended (A12 to A17), the report and status shapes of A§5.4 and the type vocabulary of A§8.3; WP2 decisions of 2026-10-14 applied (build/wp2/DECISIONS.md). Skills, templates and scripts link here and never restate it; `record.py check` looks for the strings spelled here; `tools/lint_plugin.py` asserts the three pinned sections agree with the scripts that embed them. Paths are relative to the record unless said otherwise; every example value is fictional and every owner is a role.

## Kinds, budgets and the two levels

Kinds: **current** (rewritten under the sha guard), **history** (only grows, newest first), **snapshot** (frozen when written; corrections appended as dated notes), **raw** (saved once, never edited), **machine** (JSON, script-only), **scratch** (`.work/`, never archived). Budgets are `record.py check` warnings unless marked blocking. One record per client (A14): the folder `<MMB_HOME>/clients/<slug>/` holds the client — research, calls, documents, the meeting register, the account binding and what was read from the account, the live map, the lease and the record-level close-out. Each piece of work is a strand under `strands/<id>/` and holds what dies with it. Calls and documents stay at record level because one input routinely serves two strands and is never copied; `discovery.md` is strand level because each strand is graded on its own evidence, with carry-over between strands through `SUMMARY.md` only.

## Naming and references

- **Slug**: lowercase ASCII with hyphens, at most 40 characters, legal suffixes dropped, never renamed; it is the folder name, the folder name under `archive/` after the record close and, on the GitHub archive path only, the repository name `client-<slug>` under the GitHub account in `local/settings.json`.
- **Strand id**: `NNN-<topic>`, a zero-padded ordinal assigned by `record.py strand open`, monotonic per record, never reused and never renamed, plus a topic slug of at most 24 lowercase ASCII characters. The ordinal alone (`001`) is the **short id** used in log entries, lease records, element keys and version references; the full id is the folder name.
- **Dated files**: `YYYY-MM-DD-<topic>`, with `-2`, `-3`, … for a second and later file the same day, assigned by `record.py add-transcript` and `add-document`. A transcript and its summary share one stem; a document and its snapshot share one stem. A package id is `pkg-YYYY-MM-DD`, with `-2` likewise.
- **Versions** are quoted strings (`"v0.1"`), unambiguous inside a strand. Every reference that leaves a strand folder — the live map, `account.json`, a log entry, another strand's change table, `SUMMARY.md` — is **fully qualified**: a version as `001/v0.1`, an element as `001:B1`, a frozen revision as `001/v0.1r4`; inside the strand's own ledger a frozen element reads `v0.1r4#B1`. `record.py check` blocks on a qualified reference that does not resolve.
- **Element keys**, bare inside a strand's own blueprint and ledger: `W1` workspace, `F1` folder, `B1` board, `B1.G2` group, `B1.C3` column, `B1.V1` view, `B1.FM1` form, `B1.SUB` subitems companion, `D1` doc, `DB1` dashboard, `DB1.W2` widget, `A1` automation, `PF1` portfolio, `PJ1` project, `SOP.doc` the doc copy, `U1` a UI step. A17 (2026-09-13) makes AI agents, AI columns and Vibe apps platform elements; their keys, templates and build stage arrive with the A17 design pass after the current stages and are not listed here yet.
- **Session label**: minted by `record.py lease take` as `YYYYMMDD-HHMM-xxxx`, the local date and minute of the take and four characters from `a-z0-9` drawn at random and re-drawn until the label equals none in the lock's `history`, for example `20261015-1330-k7q2`; two takes on one day never collide. A label is never free text and is compared as an exact string. Links inside the record are relative only.

## The reading contract

A chat working strand N reads `CLIENT.md`, the newest `log.md` entries, its own `STRAND.md` and strand files, `live/live-map.md`, and the `SUMMARY.md` of any strand its work touches. It never reads another strand's `discovery.md`, `blueprint.md`, `build.json`, versions or calls unless the user names one, and the front door does not offer them. A new strand may also read `CLIENT.md` with `prior_builds`, `account.json`, `meetings.md`, `research/`, every call and document snapshot, and the account live, read-only. It does not write into another strand's folder, re-open another strand's version, edit a live-map row it did not build, or adopt another strand's unverified objects during recovery.

## Section owners and the strand index

`CLIENT.md` body blocks, one owner each: folder map (engagement); strand index (`record.py`, read by every skill); `prior_builds` (engagement, appended by a strand close: per strand the archive location inside the record, the live objects we own with fully qualified keys, the allowance they consume, the client's quoted change-cost expectation and the quoted do-not-disturb list, kept even when transcripts are not); stakeholders and decision roles in the client's words (discovery-check, record-wide); recent research (engagement); links. `STRAND.md` body blocks: headline and top pains in the client's words (call-intake); verdict and top gaps (discovery-check); version and state with the approved revision's short sha (account-build and solution-audit); next step (whichever skill set it); open commitments (call-intake); open overrides (any skill, append-only); open UI steps (account-build); the `## Paused` block (`record.py`: what is unresolved while the strand is paused, by the user or by a park at a lease break, and `none (resumed YYYY-MM-DD)` after `strand resume`); links. A meeting chat rewrites its own block only, through `record.py guard`.

The strand index is one table under the heading `## Strand index` in the body of `CLIENT.md`, with this header line, a separator and one row per strand ordered by short id, the first cell being the short id; `record.py` writes it in the same locked step as any change to a `STRAND.md`, and also sets `strands_total`, `strands_open` and `current_strand`. `record.py check` reads only the lines of that block whose first cell is three digits and compares them with the folders on disk: it blocks when the set of rows or a counter differs, and warns when a title, kind, state, version, version state or clearance differs from its `STRAND.md`; `live objects` and `last activity` are display cells and are never compared:

```
| strand | title | kind | state | version | version state | clearance | live objects | last activity |
|---|---|---|---|---|---|---|---|---|
| 001 | Service desk intake | platform | active | v0.1 | approved | cleared to build | 0 | 2026-09-12 |
```

## Schemas

Front matter is flat `key: "value"` lines, every value a single-line quoted string, parsed without PyYAML, with `schema` as the first field. Inside a value `\"` is a quote and `\\` a backslash and every other character is literal; a line may end with a `# comment` after the closing quote, and a whole line may be a comment. The writer changes only the quoted value of the line it sets, keeps every other line (comments, blank lines, unknown keys, order) byte for byte, and appends a new key as `key: "value"` just before the closing `---`; a file with a parse error is refused. A skill or script that meets a schema newer than its own refuses to write. Counts and flags in front matter are strings (`"1"`, `"yes"`); in JSON they are JSON types, and every monday id is a string. Text the scripts compose is written as UTF-8 without a BOM and with LF line endings; JSON is written as `json.dumps(data, indent=2, ensure_ascii=False)` plus a final LF, key order kept; raw inputs and frozen copies are byte copies. Machine timestamps in JSON are UTC, `YYYY-MM-DDTHH:MM:SSZ`; `updated` in front matter (`YYYY-MM-DDTHH:MM`), log headers (`YYYY-MM-DD HH:MM`) and dates (`YYYY-MM-DD`) are the writing machine's local time with no zone.

### `client/2`, the front matter of `CLIENT.md`

Identity and target: `slug`, `name`, `account_kind` (`own` | `client` | `sandbox`) and `build_target` (`own-account` | `client-account` | `none`), the two agreeing (own with own-account, client with client-account, sandbox with none). Binding, each `"unbound"` until `ledger.py bind` writes `account.json.account` and mirrors it here, a difference being blocking: `monday_account_id`, `monday_account_slug`, `monday_bound_user_id`, `monday_bound_at`; `account_kind`, `build_target` and `client_workspaces` are mirrored from `account.json` the same way. Tier: `monday_tier` (`"unknown"` until read), `monday_tier_read_at` (`"never"` until read), `monday_tier_source` (`preflight` | `client statement` | `unread`). Scope and state: `products_in_scope` (comma-joined from `core`, `crm`, `service`, the union across open strands), `client_workspaces` (`"none"`, or `product:id` pairs joined by `;`, `"none"` matching an empty block in `account.json`), `record_state` (`active` | `closing` | `closed`), `strands_open`, `strands_total`, `current_strand` (a short id or `"none"`), `live_build` (`"no"` until anything of ours is live), `lease` (`"none"`, or `"<short id> <version> (<session_label>)"`, for example `"001 v0.1 (20261015-1330-k7q2)"`, mirroring the lock; a disagreement is blocking). Activity: `last_input` (`"none"`, or the stem of the newest call, document or email saved), `last_researched` (`"never"` or a date). The three open A11 fields stay at record level, asked once per client at the moment each first matters and never at setup: `transcripts_at_close` (`unanswered` | `exclude` | `archive`) and `transcript_redaction` (`unanswered` | `none` | `offered-per-call` | `always`), asked before the first real transcript or document is saved [A11-3]; `sample_data_in_account` (`unanswered` | `allowed` | `not-allowed` | `not-needed`), asked before the first revision in any strand plans sample rows [A11-2]. Then `ai_notice` (`not-yet` | `not-needed` | `given YYYY-MM-DD`) and `updated` (the local minute). `record.py check` blocks on a missing field, a value outside its set, a target that does not match the kind and a mirror that differs, and warns on an unknown field. It blocks on an A11 field left `unanswered` at the moment it matters, which it reads from three signals, and is silent at every other moment; it never fills one in. A11-3 has arrived once any save entry in `log.md` has `fixture: no` (`add-transcript` and `add-document` themselves refuse a save without `--fixture` while `transcripts_at_close` or `transcript_redaction` is `unanswered`). A11-2 has arrived when `build_target` is `client-account` and a platform or hybrid strand's `solution/blueprint.md` has `sample_rows: "planned"`. A11-1 has arrived when `account_kind` is `sandbox`, and the check then blocks while `local/sandbox-accounts.txt` under the home holds no `sandbox` line.

### `strand/1`, the front matter of `STRAND.md`

`strand` (short id), `slug` (full id), `title`, `kind` (`platform` | `non-platform` | `hybrid`), `output_class` (`configured-structure` | `bespoke-code` | `hybrid`), `opened`, `opened_reason`, `state` (`active` | `paused` | `closed`), `stage` (platform and hybrid: `new` | `intake` | `readiness` | `blueprint` | `building` | `audited` | `shown` | `signed-off` | `closing` | `closed`; non-platform: `new` | `scoping` | `handed-off` | `closed`), `version` (`"none"` or `"v0.1"`), `version_state` (`none` or a state of the table below; always `none` on a non-platform strand), `clearance` (`none` | `cleared to build` | `cleared to build, generic` | `not yet`, the string `readiness.md` carries), `override` (`none`, or the date and reason the user built past a `not yet`), `round` (`none` | `one` | `two`: which round the open version is), `workspaces` (`none`, or this strand's build-target workspaces per product once created), `next_step` (date, time, what, and `(owner: the user)` or another role), `depends_on` (`none` or short ids), `summary_current_to` (`none` or a version), `closed` (`none` or a date), `updated`. `shown` and `signed-off` are events that advance `stage`: `record.py version mark` sets it, a `shown` event leaving a stage of `signed-off` as it is, and `record.py strand close` sets `closed`; `record.py check` blocks on a stage outside the ladder for the strand's kind. Kind is set at `record.py strand open` from the user's answer and recorded with its reason, and changed only through `record.py strand kind` while the strand has no versions, with a `strand` log entry. `non-platform` means work outside monday — an application, a script, an integration against a third-party system — recorded and handed off, never designed or built (A13 as narrowed by A17). `hybrid` carries both `blueprint.md` and `scope.md`, the boundary line in each and no element in both.

### `summary/1`, `scope/1`, `version/1` and the rest

`SUMMARY.md` (`summary/1`): `strand`, `title`, `kind`, `versions` (the released versions joined by `, `), `closed`, `summary_current_to` (the newest released version, or `none`), `budget_lines` (`"80"`); then nine blocks under these headings, in order: `## What the work was` (what the work was and why it opened); `## Pains it served` (one line each, no quote over seven words); `## What was built` (qualified keys to monday ids grouped by board, each pointing at its live-map row); `## What the client confirmed` (pointers to the call summaries); `## What must not be broken` (and where that came from); `## Cost of change, in the client's words`; `## Ownership and switch-off at close`; `## Backlog seeds carried forward`; and `## Dates` (opened, shown, signed off, released and closed). On a non-platform strand the built block reads "nothing built inside the product". `scope.md` (`scope/1`): `strand`, `kind`, `boundary` (hybrid only), `updated`; seven parts in order — what exists and who built it; the scope as a delta (inherited, in scope, client-side change, access unlock); open technical questions as pointers into `open-questions.md`; external dependencies as pointers into `dependencies.md`; access needed, an owner each side and a state per item; next steps with owners and dates; process rows for human-in-the-loop work (system, owner, mode, acceptance check), never promoted into a flow spec — and then the fixed final section, which `record.py check` and `tools/lint_plugin.py` look for verbatim:

> Building this work happens outside this product. This record holds its scope, open questions, dependencies, access needs and next steps; it does not design or build it.

`version.md` (`version/1`): `strand`, `version`, `qualified_version`, `state`, `purpose` (`proof-of-concept` | `working-solution`), `revision` (`"none"` or an integer string), `sha256` (`"none"` or hex), `opened`, `released` (`"none"` or a date), `shown` (`"none"` or dates joined by `; `), `signed_off` (`"none"` or a date), `close_reason` (`"none"` until `client-closeout` writes the reason through `guard`) and `updated`; the body carries `## Scope`, `## Build`, `## Reactions` and `## Events`. Each event `record.py version mark` records is one entry under `## Events`: `### shown YYYY-MM-DD` with the lines `- audience: ...`, `- account: ...` and `- words: "..."`, or `### signed-off YYYY-MM-DD` with `- by: ...`, `- words: "..."` and `- unconfirmed structural assumptions:` followed by one indented line per item, or `none`. `blueprint/1` (`solution/blueprint.md`) carries `sample_rows` (`"planned"` | `"none"`, shipped `"none"` and set by `solution-blueprint` when the current revision plans sample rows; `record.py check` blocks on `"planned"` with `solution/exclusions.md` absent). ### `lock/2`, `.work/lock.json`, the lease

Written only by the lease primitives in `mmb_common.py`, which `record.py lease` and `ledger.py` call; a take, a refresh, a release, a break and a repair are state changes and the file is never deleted. Fields, in this order: `schema`, `kind` (`build`), `epoch` (an integer, `0` before the first take), `strand`, `strand_title`, `version`, `run_id`, `session_label`, `taken_at`, `heartbeat_at` (each a string while `state` is `held` and `null` otherwise), `state` (`none` | `held` | `released` | `broken`), `history[]`; there is no `surface`. Every take and every break increments the epoch by one, with no special case: breaking a lease held at epoch E leaves the lock at E+1 in state `broken`, and the next take, the taker's on a park or the fresh holder session's on a resume, makes it E+2. A heartbeat older than 60 minutes reads stale; nothing expires on its own. A history entry is appended on a take, a release, a break, a park and a repair, never on a refresh: `{event, at, epoch, strand, version, session_label, run_id, by, choice, reconcile, note}` with `event` `taken` | `released` | `broken` | `parked` | `repaired`, `at` in UTC, `by` the acting session's label (the minted label on `taken`, the holder's on `released`, `null` on `broken`, `parked` and `repaired`, because the acting session holds none), `choice` `resume` | `park` on a break and `null` otherwise, `reconcile` the class counts of the classify-only run on a break and `null` otherwise, and `note` on a break and a park the taking strand and the user's quoted words (`for 002: "..."`), on a repair what it was rebuilt from and the user's words, and `null` otherwise. A `broken` and a `parked` entry also carry `for_strand`, the strand the break was run for, and a `repaired` entry carries `for_strand`, the strand the repaired lock is kept for, or `null`.

**Whose take comes next.** While the lock is `broken`, its newest history entry keeps the lease for one strand, and `lease take` refuses every other: after a break with `resume`, the holder's strand (its fresh session runs the ordinary recovery); after a park, the `for_strand` of the `parked` entry; after a repair, the `for_strand` of the `repaired` entry. A reservation for a strand that has since closed lapses. `record.py lease status` and `status --json` show it as `reserved_for`.

**Writes and repairs.** A primitive writes both mirrors first and the lock last, so a write that fails leaves the lease as it was and the same call can be retried. A take, a release, a break and a repair back the lock up first (`.work/backup/.work/lock.json.<stamp>`); a refresh does not. The fence that `ledger.py` calls before every account-affecting write passes only while a run has started under the lease and is the presented one, and when it passes it moves the heartbeat in the same hold. A run id enters only the lease it started under. `record.py lease sync` rewrites both mirrors from the lock, the lock unchanged; `record.py lease repair --user-yes "<the user's words>"` rebuilds a missing, torn or malformed lock in place, never by a delete: one epoch above every epoch the newest sound lock backup and the `account.json` mirror know, with that backup's history and a `repaired` entry, in state `broken` kept for the strand the mirror names as holder (or the backup kept it for), else `released`, and a record-level `lease` log entry. The two mirrors, `lease` in `CLIENT.md` and `account.json.guard_index.lease`, are written in the same call, and `record.py check` blocks when either disagrees with the lock (naming `lease sync`) and when the lock's shape is not the one above (naming `lease repair`).

## Version states

Per strand; a `non-platform` strand has none. `planned` → `approved` → `building` → `built` → `audited` → `released`, with `fixing` between an audit that fails and the retry; `shown` and `signed-off` are events recorded in `version.md`, never states. The files `record.py check` requires, relative to the strand:

| State | Files required |
|---|---|
| `planned` | `solution/blueprint.md`; `versions/<v>/version.md` with `revision` not `none` and a `## Scope` heading |
| `approved` | `versions/<v>/blueprint-r<N>.md` whose sha256 equals `version.md` `sha256`; the approval entry in `build.json.approvals` for that version and revision; an `approval` log entry at the strand position with that version |
| `building` | a `runs[]` entry in `running` for the version with `lease_epoch` and `another_build_running` set; `.work/lock.json` held by this strand; `change_check.for_strand` in `account.json` this strand; `preflight.version` this version |
| `built` | a `## Build` heading in `version.md`; a `build` log entry |
| `fixing` | an `audit*.md` with a `## Findings` heading |
| `audited` | the newest `audit*.md`, with `## Write detection` and `## Documents appendix` headings and a last non-empty line `cleared to show` or `not cleared to show` |
| `released` | `versions/<v>/build.json`, `backlog.md` and `log.md`; from `v1.0` a `signed-off` event in `version.md` |

A version's required files are those of its current state's row and of the rows it has passed through, except that `building` and `fixing` are checked only while current. A missing file is a warning in every state but `released`, where it is blocking, and `record.py version release` refuses on any missing file of the rows it needs; condensed current files are not checked by a script. `presented` in `export.md` is accepted for a v0.x export and blocks v1.0.

## The log

`log.md` (`log/1`, front matter `schema` and `client`) is one record-wide history, newest first, entries never edited, written only by `record.py log`, which re-reads the file and inserts under the header. An entry is this header line, then at most five lines:

```
## YYYY-MM-DD HH:MM · <strand or -> · <type> · <version or -> · <key or session label>
```

The strand position is the short id, or `-` for a record-level event (a binding, a research pass, a lease break, a record close); the version is bare because the strand position qualifies it. Types, 44 in all, embedded in `record.py` between pinned markers so that `tools/lint_plugin.py` can assert the list agrees with this one: `created`, `binding`, `workspace`, `research`, `call`, `document`, `email`, `conflict`, `readiness`, `override`, `superseded` (only the same commitment from the same speaker inside one call; any other pair is a `conflict`, with no arithmetic between the two), `scope`, `blueprint`, `approval`, `change-check`, `preflight`, `build`, `departure`, `irreversible`, `automation`, `workflow`, `agent`, `ai-column`, `vibe`, `sequence`, `webhook`, `write-failed`, `recovery`, `audit`, `write-detected`, `shown`, `signed-off`, `lint`, `version`, `release`, `strand`, `lease`, `live-map`, `summary`, `api-surprise`, `decision`, `commitment`, `closeout`, `archive`. A save of a call, document or email is one entry at strand position `-` and version `-`, type `call` (a transcript), `document` or `email`, key the stem, with exactly these body lines: `path: <record-relative path>`, `sha256: <hex of the saved bytes>`, `input_kind: <transcript|document|email> · fixture: <yes|no> · asked_by: <short id> · redactions: <n>` and, for an attachment only, `came_with: <record-relative path of the email input>`. A roll moves whole entries, verbatim, out of the record log: at a release every entry at the strand's position whose version is the released version moves into `versions/<v>/log.md`, and at a strand close every remaining entry at the strand's position moves into `strands/<id>/log.md`. Each rolled file is new, with front matter `schema: "log/1"`, `client`, `strand`, `version` (or `"none"`), `rolled_at`, `entries` and `sha256`, and each roll leaves one pointer entry at the strand position (type `release` with key `released`, or type `strand` with key `closed`) whose body is `rolled_to: <record-relative path>` and `entries: <n> · sha256: <hex>`. An entry's hash is the sha256 of its header and body lines with line endings normalised to LF, and the roll hash covers the moved entries in file order. `record.py check` blocks when a rolled file's recomputed hash differs from its front matter or its pointer entry, and, by the baseline `.work/history.json`, when an entry was changed or removed; it warns on an entry absent from the baseline and on a missing baseline, which the next insert rebuilds.

## Evidence markers and the citation contract

| Marker | Meaning | Travels with it | Counts toward the rubric |
|---|---|---|---|
| `[Q]` | client quote, verbatim, never tidied; intake `certain`, or `probable` with the qualifier travelling with it | speaker name and role, side, location | yes, client side only |
| `[Q?]` | quote with an unclear speaker (intake `uncertain`) | as `[Q]`, plus a note | Partial until the user confirms |
| `[Q/side]` | side-only quote, speaker not resolvable (intake `unattributable`, or a segment of a composite block) | the side, the unit or block range, a note | Partial, never Missing |
| `[Q/recon]` | a sentence assembled from several units after boundary de-duplication | as `[Q]`, plus every unit number | as the weakest unit it rests on |
| `[Q/doc]` | a verbatim extract from a client document (A16) | the document, its section or page, the author by role where known, the document's date and status | yes for current-state and requirements criteria; cost, why-now, decision-process and next-step only where stated explicitly |
| `[X]` | quarantined: spoken inside a demonstration frame that is ours with a screen shared, or under a hypothetical marker | the frame's location and the reason | never |
| `[E]` | external fact from a dated source | source key `S#` from the register | no |
| `[I]` | inference | its basis and a confidence word | no; it can only shape a question |
| `[A]` | assumption: a build decision made without evidence, from the readiness check's assumptions, including an assumed term (an automation condition or the board-architecture overview not yet confirmed) and a fork built on its leaning (A25) | its basis, the question that would replace it, and, once the user reports it, the client's confirmation or explicit acceptance, which clears it | no; it shapes the build and the next questions, stays assumed until cleared, and is never written into monday as if the client had said it |

Locations follow the file's own grammar: `@HH:MM:SS`, `cue 82`, `cues 82-85` for a merged run, `L142` or `L142-144`, `paragraph 75`; a document extract cites `inputs/<stem>.md §3.2` or `p.4`. Markers live in `research/`, `calls/`, `inputs/`, `readiness.md` and the internal parts of the blueprint; `leak_lint.py` blocks all nine in `sop/`, `drafts/`, `deliverables/` and every monday payload. Four tiers: attributed (`[Q]`), attributed with a qualifier (`probable`, or `[Q?]`), side-only (`[Q/side]`), refuse; a `[Q/doc]` whose author is known is attributed, otherwise "the client's document", one step below. Refusal is mandatory for a sub-clause fragment, a re-joined sentence whose load-bearing half changed speaker, a quote resting on an assembled figure, a second-hand re-quote of another call, and any quote whose first or last word sits under another speaker's label — the speaker boundary, never the turn boundary.

| `assumptions[]` | `statement`, `question` (the question that would replace it), `kind` (`gap`, `call-type`, `automation-condition`, `board-architecture` or `leaning`), `state` (`assumed`, or `accepted` where the user has accepted it on the client's word); a confirmed assumption becomes evidence and leaves the list (A25); in `readiness.md` each assumption is one line under `## Assumptions`, `- <statement> [kind: <kind>; state: <state>]`, with its question on the next line as `  question: <text>` |
| `unmet_needs[]` | `need`, `clock` (or null), `why_not_met` |
| `ai_opportunities[]` | `pain_or_need` (a pain id or a need), `kind` (`agent`, `ai_column`, `workflow`, `vibe_app` or `sequence`), `round` (`1` only when the client asked for AI or workflows on the call, otherwise `2`), `probe_basis` (`P-19`, `P-20`, `P-21` or `unprobed`), `idea` (one sentence) |
| `verdict` | `cleared_for` (`build`, `build-generic` or `not-yet`), `conditions[]` (always the approval stop, and the A11 question that first matters where one does), `reason` (one sentence) |
| `questions[]` | at most five, ordered: `text`, `kind` (`read-back` where a signal exists, `discovery` otherwise), `role` (who can answer), `known` (what the record already holds) |

`cleared_for` is the machine value, kept in the body for solution-blueprint; the check says it to the user as a human string, and the front matter of `readiness.md` (`clearance`), `STRAND.md` and the approval card carry the string: `cleared to build`, `cleared to build, generic`, `not yet`, or `none` before the check has run. `record.py check` reads only the front-matter field, blocks on any other value, a machine value included, and warns when it differs from `STRAND.md` `clearance`. `build` is `cleared to build`: at least one pain with an entity and a wanted outcome, the product chosen, the structure stated with its leanings, the build target named. `build-generic` is `cleared to build, generic`: the same, with the structure resting mostly on assumptions; the build goes ahead as a generalised version, the assumptions list is the agenda for the next contact, and the approval card's "what this build rests on" section is the user's yes to them. `not-yet` is `not yet`: no pain or entity firm enough to build on; the questions are the next step. A fresh `readiness.md`, before the check has run, carries `none`, which is never a result of the check. solution-blueprint reads the machine value, and `not-yet` or `none` stops the blueprint unless the user overrides with a reason, logged as `override` (plan decisions D1 and D2). No grade, R-number, gate name or sales verdict appears in the block; those lists are v2 and are tagged so above.

The two modifiers' values are pinned here because the design names the modifiers without values: room shape counts the client attendees, and a group, the small-group value, is two or more client attendees, below the large-room threshold, so a call with two client attendees is small-group (widened from "more than two" by plan decision D3 in the fixture fix pass); money is live when a commercial marker is spoken, split by whether the person who approves spend is in the room (method §4.10).

Each field is written as its value followed by its state, `detected`, `proposed` or `confirmed`; an unresolved field is written `unresolved`, and the header lists its `candidates` and the fallback applied. Detection proposes and never decides; an unresolved dimension demotes every type-specific rubric rule to advisory and never a door.

The thirteen labels, the `call_type` value, the type stem in a call's file names and the routing key of A§8.3 step 7: `intro`, `discovery`, `reverse-demo`, `prototype-review`, `demo`, `scoping`, `working-session`, `pricing`, `call-review`, `expansion`, `sign-off`, `check-in`, `support`.

## Pinned: permitted-constants

The only constants transcript_measure.py may hold. Every threshold it applies to a unit is derived from the file's own distribution at these ranks, floored by these absolutes and softened by these bands, so no constant expresses turn grammar directly: there is no word count that makes a fragment and no gap that makes a wedge. Every backticked token in this section is embedded between the script's pinned markers, and the lint asserts agreement; the values applied travel in the intake report.

| Constant | Value | Class | What it governs |
|---|---|---|---|
| `min_units` | `80` | minimum unit count | with fewer raw units than this nothing is derived: the floors apply alone and the report says so (the short reviewed fixture has 75) |
| `p_short` | `0.1` | percentile rank | words per unit at this rank of the file's distribution: the short-unit threshold |
| `p_long` | `0.9` | percentile rank | words per unit, and seconds per unit where end times exist, at this rank: the long-unit thresholds |
| `p_gap` | `0.9` | percentile rank | the inter-unit gap at this rank: the wide-gap threshold |
| `p_rate` | `0.95` | percentile rank | words per second at this rank, where end times exist: the implausible-rate threshold |
| `floor_short_words` | `3` | absolute floor | the short-unit threshold never falls below it |
| `floor_long_words` | `60` | absolute floor | the long-unit word threshold never falls below it |
| `floor_long_seconds` | `45` | absolute floor | the long-unit seconds threshold never falls below it |
| `floor_gap_seconds` | `2` | absolute floor | the wide-gap threshold never falls below it |
| `band_units` | `0.15` | no-action band width | the fraction either side of a derived word or seconds threshold inside which a unit is reported borderline and no detector fires on it |
| `band_gaps` | `0.15` | no-action band width | the same, around the wide-gap threshold |
| `composite_cutoff` | `0.03` | few-percent cutoff | the share of words inside composite blocks above which talk share is refused and the pass is marked cautious |
