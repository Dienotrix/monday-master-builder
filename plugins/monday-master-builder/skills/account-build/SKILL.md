# Account build

Internal working instructions. Every write follows one path: `ledger.py intent`, `leak_lint.py payload`, the monday call, `ledger.py record`, a read, `ledger.py verify`. The ledger is what makes a build resumable and auditable, so nothing is written to monday outside it. Lean version written from demo 1 and revised from demo 2 (A31); the exact command forms and read shapes are in [write-path.md](references/write-path.md).

A build runs the plugin's three scripts a few hundred times, and the connector's write tools the plan needs (`create_board`, `create_column`, `create_items`, `create_view_table`, `create_automation`, `create_dashboard`, `create_widget` and the raw `all_api_write`). The session needs all of them allowed before the first command, or the run stops half built. A call the session refuses never reaches monday, but leaves its row `attempting`, like a timeout (see write-path, "When something goes wrong").

## Stop before writing when

- The strand is `non-platform`, or its version has no approved revision: the user's yes to the card comes first.
- The home has no `local/settings.json` with the firm name: `leak_lint.py payload` cannot run without it, and a payload it has not checked is never sent.
- The connector's account or user is not the one the record is bound to: show both and ask the user to reconnect.
- Another strand holds the record's build lease: say which, and wait.
- A connector tool the plan needs is missing from the session: the change check stops the build.
- The frozen revision lists an element kind this skill does not say how to build: stop and ask, or build it as a probe only on the user's word, logging what monday made.

## Before the first write

1. Read the frozen revision, `versions/<v>/blueprint-r<N>.md`, and build only what its element-key table lists. Where its sections disagree with each other (a view's columns in section 12 and in section 16's build checks), follow section 16 and say so in the build notes. Hold the user's words of approval.
2. **Bind** the record to the account once: read `me { id kind } account { id slug name tier products { id kind } } version { kind value }`, save it as `.work/inputs/bind.json` and run `ledger.py bind --binding .work/inputs/bind.json`; then write the mirror it prints into `CLIENT.md` through `record.py guard`, with `monday_tier` set to the tier the read returned and `monday_tier_source` to `preflight`, since the mirror leaves them out.
3. **Approve:** `ledger.py approval --strand <id> --version <v> --revision <N> --sha256 <frozen sha> --words "<the user's words>" --session "<date> build session"`, with `--irreversible` for every workspace and folder row the build creates and `--referenced` for every row that already exists, such as a named test workspace. Native installs and automations, which the card lists as hard to undo, take the card's own yes on a proof of concept in the user's account (A28), not the flag. Set `version.md` `state` and `STRAND.md` `version_state` to `approved`.
4. **Change check:** compare the session's connector tools with the roster in `shared/monday-gotchas.md` and the ring with `version { kind value }`, save the result as `.work/inputs/change-check.json` and run `ledger.py change-check --from …`. Tools the session has beyond the roster go in `added`. The file holds `ring`, `versions_seen` (a list), `release_notes_since` (`"<date> (read)"` or `"not-read"`), `roster_diff {added, removed, renamed}` (three lists), `schema_diff` (a list), `result` (`no change affecting this build` or `change affecting this build`) and `approved_by_user` (null, or the log reference of the user's yes). A removed tool the plan needs stops the build for the user.
5. **Development only (A31):** when the build goes into the test workspace the user named, run `tools/dev_test_workspace.py --record <folder> --strand <id> --workspace <id>` from the plugin repository.
6. **Lease and run:** `record.py lease take build --strand <id>` returns the epoch and a session label; `ledger.py run start --strand <id> --another-build-running no --account-check match` returns the run id. Hold all three in the session for every write; never read them back from the lock. Set `version.md` `state` and `STRAND.md` `version_state` to `building`, and `STRAND.md` `stage` to `building`; the audit moves the stage on. Write the revision's planned UI steps now, each with `--key` as the table names it, so a departure later (which mints the next free U number) cannot take a planned key.
7. **The referenced workspace:** `verify` is fenced, so `W1` is verified only now, with a read that shows its id, name and kind, and `workspace_id` equal to its own id. It takes no `intent` and no `record`.

## The build, in this order

Build in phases and batch the bookkeeping: run `intent` and the payload check for every element of a phase, make the calls, then `record` and `verify` each one. A refusal is read and fixed, never retried blindly.

1. **Folder and boards.** Create a board with raw `create_board(… workspace_id, folder_id, empty: true)`: the `create_board` tool drops the folder. Rename each new board's default group to the first planned group: its row is an `intent --operation create` with the `update_group` payload, recorded under the id `topics`.
   **A native install** (a row with a `template` cell, A38): `intent` with `--template-id <id>`, then raw `create_board(board_name, board_kind: public, workspace_id, folder_id, template_id: <id>)`, one board per call. Several in one request can time out and still all be made (G-157), so read the workspace before any retry. Archive the template's own items in batches of about 20 with aliased `archive_item(item_id:)` (G-160), then verify the board with a read carrying `created_from_board_id` (the template id) and `items_count` (0, since archived items are not counted). The ledger then registers it as a native this strand installed.
2. **Columns.** Status and dropdown labels as objects, with ids; label ids may stay the numbers monday returns, 0 included. A date that needs a time gets `show_time_by_default`. Connect columns are created two-way (A32): `allowCreateReflectionColumn: true`, which adds the other board's connect column, named "link to <board>". Run that column's `intent` before the call that creates it, then rename it to its planned name with a title-only change and record it under its own key. A column already built one way becomes two-way by `update_column` with the same setting and `boardIds` resent. A formula takes its settings from `get_column_type_info` and is verified on its `display_value` once the rows exist (phase 4).
   **On an installed native,** the template's own columns are changed under this approval with `intent --operation update` and the existing column's id. A relation the template left empty names the board it was meant for as the key of its `dataSourceLayoutConfigs`. Link it with `update_column` and `{"boardIds": [<installed board>], "allowCreateReflectionColumn": true}`, two-way whether or not the template set the flag (A32, G-158). Each column has its own `revision`: read each one before linking, never reuse another column's. Rename each reflection column monday adds ("link to …") and record it under its own key. Before adding a planned column, look for a template column of the same name and type (the v2 Leads template brings a Region status, the v2 Deals template a Last activity date) and take it as an update row instead of a second column of the same name. Sales Activities' source-item relation cannot be re-pointed (G-159). A template's own form view (Leads' Web Form) is left as installed; read its login setting and list it for the user.
3. **Groups.**
4. **Sample rows,** by item batch, at most 20 per `create_items` call. Create the rows a connect column points at first, then the rows that link to them with `item_ids`, each linked batch's `intent` carrying `--ref board:<the target board's id>`. Date-column times are UTC.
5. **Mirrors,** once both boards and their connect columns exist. A date mirror's earliest or latest is `calcType` (`earliest`, `latest`), named in `get_column_type_info`'s mirror schema. Its `display_value` still lists every linked date (G-31); a formula over it sees the aggregate, so check the formula, not the mirror's text.
6. **Views and forms.** Table views with their filters and sorts, sort directions in capitals (`ASC`, `DESC`): a lower-case `desc` is stored ascending. A view that shows only some columns stores the rest as hidden (G-87). Read them back with `get_board_info` views and check each stored sort direction and hidden column. A form view starts with every column as a question and is open to anyone with the link: hide the questions the blueprint leaves out, set its title, and turn on "require login" before anyone sees it.
7. **Automations,** after everything they read. `create_automation` with the trigger, the action, and for a notification monday's own "Notify someone" action named in the prompt, with the user by name: left to choose, the tool can pick another product's notify block and store nothing. A date trigger names a time of day, which monday stores in the account's timezone. Change a status, set a date to today and move an item to a group resolve from plain names. A condition goes in its own block (write-path gives the shape). Read back with `list_automations` and check the trigger column and label, the offset and time, every condition and its `shouldCheckIfStatusIsNot` (monday can store "is" as "is not", G-161), the action block and its target (column, label, date value or group), the receiver, and every field the message reads: a placeholder can be mapped to the wrong column. The stored title is the raw prompt (G-66). A wrong automation is never patched with a second one, since nothing deletes one from outside: verify it `mismatch` and `depart` it with decision `ui-step`, so the user fixes that one field in monday.
8. **Dashboard and widgets.** `create_dashboard` with the board set and the folder (the set cannot change later, G-90); widgets from `all_widgets_schema`'s properties only (G-63). Verify the dashboard through the search tool with its `id`, `workspace_id`, `name` and `kind`; search does not show the folder, so its place rests on the create call. Widgets cannot be read back (G-11) and are verified `not-checkable` with a note; they stay `written` in the ledger, so a count of verified rows leaves them out. A date axis can group by month as well as by week.
9. **UI steps:** the planned ones are written at the run's start (step 6 above); a departure adds its own. Each takes `ledger.py ui-step`, owner the user, with `--target-version` and without the fence.

## After the last write

1. `ledger.py run end --strand <id> --calls-used <n>` writes the live map and releases the lease. Write each `log` entry a ledger command prints through `record.py log` as soon as it is printed.
2. A departed element that is still live in monday, such as an automation, reaches the live map marked departed; name it in `version.md` `## Build`, and for an automation write a UI step to switch it off in monday, since the ledger takes no write on a departed row.
3. Set `version.md` `state` to `built` and write under `## Build` what was built, what was verified, what was not checkable and what departed; set `STRAND.md` `version_state` to `built`.
4. Run `record.py check` and `ledger.py check --strand <id>`; both should be clean.
5. Tell the user: a link to each board and the dashboard, what each view is for, which automations will notify them and when, that the build switches them off when the user says the demonstration is over, the UI steps left to do, and anything that did not go as planned. The audit (`solution-audit`) is the next step before the demo is shown.

## Switching the automations off

Automations are live from the moment they exist. When the user says the demonstration is over, or asks for them off, the build switches them off itself: `manage_automations` deactivate works on an automation the API made, and `list_automations` reads the state back as `is_active` (G-65). It is one short run through the write path.

1. Take the lease and start a run, as in "Before the first write", step 6; there are no UI steps to write.
2. For each automation row that is `verified` and `active`: `intent --operation update --notifies user`, the payload check on `{"action": "deactivate", "workflowId": "<id>"}` with `--kind automation`, `manage_automations` deactivate, `record --id <the same id>`, a `list_automations` read on its board, and `verify --result match` when the read shows `is_active` false. The ledger then holds the row `inactive`.
3. A departed automation takes no `intent`, so it stays a UI step for the user; name it.
4. `run end`, the log entries, `record.py check` and `ledger.py check --strand <id>`. Tell the user which automations are off, and that one is turned on again the same way with `activate`.
