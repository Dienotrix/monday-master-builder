# Build readiness

Internal working instructions. The check answers one question: does the record hold enough to build a proof of concept worth showing, and if not, what exactly would close the gap. Its output is the first section of the approval card, so the user approves the assumptions with the structure. Lean version written for the demo-first work (A31); the full skill follows ARCHITECTURE A§3.3 and A§8.4, BUILD-PLAN WP19 and `build-readiness-spec.md`. The file's shape is in [readiness-guide.md](references/readiness-guide.md).

## Always

- Thin input never blocks the check. It widens the assumptions and makes the first build more generic, because a basic demo beats waiting for better inputs (A27).
- Evidence is the client's words as the summaries quote them, at their locations. Copy a quote from the summary as it stands, with the location of the line it came from (a quote reused in a question keeps its own), or check it against the saved input; never quote from memory.
- The user's side's framing, recaps and demonstrations are not client evidence, `[X]` seed data is never a fact, and an inference only shapes a question. An item under a summary's `## Agreed` is scope the client confirmed: it may frame the build and settle a leaning, but it is never a goal, which needs the client's own words.
- Nothing the client did not give is passed off as theirs. A number, threshold or automation of our own is marked `ours, provisional: <figure>` in its assumption for the user to correct, and an automation enters only where a pain or a stated wish asks for it.
- An assumption is labelled as one, with the question that would replace it, and stays assumed until the user reports the client's confirmation or acceptance (A25). It is never written into monday as text.
- A conflict between two calls, or between a document and a call, keeps both statements and becomes a question. The most recent statement does not win.
- The check never asks whether the client is ready to buy: no grade, score, gate or sales verdict appears.
- It makes no monday call. What exists in the account comes from the record.
- Nothing written names the user's firm, the plugin or the assistant, and quotes stay inside the record.

## Before anything

- Run the scripts with the plugin's Python: `python3` on macOS, `py -3` on Windows, or the exact version the environment names, as in `[python] ${CLAUDE_PLUGIN_ROOT}/scripts/record.py --record <client folder> <command>`. Every script prints one JSON object; exit 1 is a refusal to read and fix, exit 3 means it could not run. Each `record.py` write also refreshes the home's `clients-index.json` (digests only), which is expected.
- Work inside the client's folder. Read `CLIENT.md` (the build target, the binding, the tier), the strand's `STRAND.md`, its current `readiness.md`, its `solution/exclusions.md`, every summary under `calls/` and `inputs/` whose `strands` names this strand or reads `unassigned`, `live/live-map.md` if it exists, the account block of `account.json` when the record is bound, other strands' `SUMMARY.md` when there are any, and the research brief if one exists. Where an input has no summary yet, run `call-intake` first.
- A `non-platform` strand gets no readiness check: say so and point at its `scope.md`.
- Run over the whole strand, every input together, not the newest one alone. Where `readiness.md` already holds a part that nothing new touches, keep it.
- Stage every file you write through the guard in the record's `.work/staging/`, and delete that folder after the last write.

## The parts, in order

1. **Goals, pains and signals.** The client's goals first, in their own words with quote, location and speaker role, each linked to the pains it relates to; where the input states no goal, say so in the note. Then each pain with its quote, location, role, stated or excavated, and the wanted outcome in the client's words, or none. Carry every pain line of the summaries: never drop one because its theme already has a line. A workaround kept by hand, a "will not survive growth" line and a pain the client defers (marked `deferred`) each get a pain line and an element, not only a signal or an unmet-need row. Then the signals the user's side never confirmed, which point the next question and are never evidence.
2. **Entities and how they move.** Carry every entity of the summaries, children and neighbours included: intake routes, owners, stages, steps, agreements, money fields, roles, kinds of event, locations, today's artefacts (also listed under `## Existing`) and outside approvers. For each: its parent, whether it moves independently (its own dates, owner, status or expiry), whether it is a shared resource (booked or reused across many), whether it goes stale (produced from data that later changes), and the source: spoken, observed, documented or assumed. Set each flag from that entity's evidence, never by the kind's usual value. Answer in writing for every parent and child: what moves independently of what.
3. **Product fit.** Name the product per entity. A sales pipeline (leads, deals, contacts, accounts, sales activities) is CRM; requests, tickets and incidents are Service; projects, jobs, tasks, assets and the rest are Work Management. CRM and Service entities live on the account's native boards (A5, [native-objects.md](../../shared/native-objects.md) sections 3 and 4), never on a look-alike. Preflight finds the native set in the workspace, or the build installs it from the native templates when the workspace is bare (section 6.6); neither is a condition here. Where the client's word for a native entity differs from the board's, record it in the native reuse line as the client's word; the blueprint plans any relabel, and a native the build did not install is never renamed (section 6.3). Dev is named and not built. An Enterprise Work Management client gets a portfolio by default (A6): when the tier is unknown, assume no portfolio and ask the tier.
4. **Structure.**
   - The build target from `CLIENT.md`, with its reason: `CLIENT.md` `build_target_reason`, which `init` writes, else the record's default; where an input offers another target, that is an assumption. Then one new workspace per product named for the client (`<name> – Ops` for Work Management, `<name> – CRM`, `<name> – Service`), unless the build continues workspaces already built for this client (A21).
   - Where children move independently of a parent, apply the parent-row-with-roll-up pattern; on native boards the children are connected rows of their own board. Where one pursuit carries several documents from an outside system (a quote reissued, a version resent), lean to the pursuit as parent with each document as a child row and a roll-up, on the condition of how often a second document happens.
   - Where the evidence does not settle a shape, record a leaning: the question, the option the evidence leans to, its quotes and locations, and the condition that would settle it; two client speakers who disagree make a `fork`.
   - Each route records arrive by gets its element (a form for one at a time, an import for lists), and each constraint its structure (who sees what, what stays untouched, the effort a task may take). A value keyed by hand from another system gets a `<system> status as of` date beside it, so staleness shows.
   - Then answer for every pain: which element fixes it, and does the shape fix the pain or copy today's tool. A pain with no element is a finding: write `none` with the reason.
5. **What already exists.** From the live map and `account.json`, each object with its constraint; a `do-not-change` row limits what can be cleared. When nothing is bound, write "unknown, no account bound". Then the client's current tools by category, field by field: what each stays the system of record for, and what the build only follows.
6. **Assumptions.** One line each, with its kind and state, and its question on the next line. The kinds: `gap` (a missing fact the build fills), `call-type` (when intake could only guess the type), `automation-condition` (each trigger and condition the build will use, until the client confirms it), `board-architecture` (the general overview of the boards, likewise) and `leaning` (each leaning or fork the build rests on). Use the kind for what the line is: a structural choice with a settling condition is a `leaning` or `board-architecture`, never a `gap`. Write one for each thing the input raises and leaves open, handover work included: data brought across or left behind, what becomes of an earlier attempt or an abandoned board, sample rows invented with no real names, a goal or test set by someone not on the call (to confirm with them), a client name taken as a placeholder, a build target an input offered, and a constraint the build can only approximate. Column names and status labels are not assumptions; the user checks them on the card.
7. **Unmet needs.** Anything the client needs that v1 cannot build or has not probed, with its clock where the client gave one; a constraint whose design is not yet probed is one as well as a structure line. A product limit never deletes a client need. Work outside monday is named here and handed off (A13).
8. **AI and workflow opportunities.** Each tied to one pain or stated need and one element kind: `workflow`, `agent`, `ai_column`, `vibe_app` or `sequence`. Round `1` only when the client asked for AI or workflows; otherwise `2`, built after the first showing unless the user sets another cadence (A27). The probe basis is `P-19` for an agent, `P-20` for a Vibe app, `P-21` for a workflow, and `unprobed` for an AI column or a sequence. No credit figure, price or package.
9. **The clearance and its conditions.** One of the record map's three strings, written in the front matter, with the machine value under `## Verdict`:
   - `cleared to build` (`build`): at least one pain with an entity and a wanted outcome, the product chosen, the structure stated with its leanings, and the build target named.
   - `cleared to build, generic` (`build-generic`): the same, with the structure resting mostly on assumptions. The build goes ahead as a generalised version, and the assumptions are the agenda for the next contact. It needs no separate yes: the card's "what this build rests on" is that yes.
   - `not yet` (`not-yet`): no pain or entity firm enough to build on. The questions are the next step.
   The conditions beside it are never the check's to clear: always the approval card; an A11 question that first matters now (sample data when the build target is the client's own account); a workspace not yet named (a CRM or Service build needs a workspace in that product, A37); a probe not yet run for a kind the build plans. On an own-account build the workspace is the user's and solution-blueprint names it: an unbound client account is no condition, so word nothing as if the build waits on one. A native board automation has no probe and adds no probe condition.
10. **Questions for the next contact.** At most five, ordered by what they unblock. Ask one per unresolved structural choice before a second variant of one already asked: who owns a record two people touch, who inherits a leaver's records, and who keys a value carried by hand from another system each earn a question of their own. Each is a read-back of the client's own words where a signal exists, and a discovery question where none does; each names the role that can answer and what the record already holds. A conflict shows both statements. A leaning carries its option and its settling condition. Five stays the ceiling on thin input: a generic build carries more assumptions, not more questions.

## Writing and checking

1. Where the client asked that something stay private, or out of what is shown, check that `solution/exclusions.md` lists it. If not, add the row through the guard in the form the leak lint reads, `- <term> [kind: name; added: <date>; by: the user; source: <summary path and location>]`, one row per line under the template's `## Exclusions` heading. The lint enforces only what that heading lists.
2. Write `readiness.md` in the guide's shape. It exists from the template, so read its sha first, `record.py --record <folder> guard --strand <id> --file strands/<strand folder>/readiness.md`, then write: `guard --strand <id> --file strands/<strand folder>/readiness.md --expect-sha <sha> --from <staged file>`.
3. Set `STRAND.md` `clearance` to the same string, `stage` to `readiness`, and `next_step` to the blueprint or, on `not yet`, to the questions (owner: the user), through the guard. Also write `STRAND.md`'s `## What this build rests on`: `- clearance: <the string>`, `- assumptions: <n> in readiness.md, <n> structural`, then each structural assumption line as `readiness.md` writes it, without its question. `record.py` updates the strand index inside `CLIENT.md` with it. When the products differ from `CLIENT.md` `products_in_scope` (`core` for Work Management, `crm`, `service`), set it there through the guard as well, reading `CLIENT.md`'s sha only after the `STRAND.md` write, since that write changed it.
4. Log it: `record.py --record <folder> log --strand <id> --type readiness --key "<clearance>" --line "<goals> goals · <pains> pains · <assumptions> assumptions · <questions> questions"`.
5. When the full skill writes `solution/open-questions.md`, it starts it from `templates/record/open-questions.md`. Run `record.py --record <folder> check` and fix what it blocks on; a quote marker with no location on its line is a warning to fix. Delete `.work/staging/`.

## Hand back

Brief the user in at most eight lines, in this order: the goals and the top pains in the client's words, the product and the workspaces, the clearance with its reason, the main assumptions the build would rest on, the questions for the next contact, and the next step. On `cleared to build` or `cleared to build, generic`, the next step is `solution-blueprint`; when the user asked for a demo or a build, go on to it, since the card is where they say yes. On `not yet`, show the questions and stop; the user may override with a reason, which `solution-blueprint` records. The check is run again after any new input, or after the user corrects the call type.

## Stop and ask when

- The strand is `non-platform`.
- Two client speakers disagree on something the whole structure turns on, and the record gives no leaning: ask which way to lean, and record the answer as the user's.
- An input in the record has no summary and cannot be summarised now.
